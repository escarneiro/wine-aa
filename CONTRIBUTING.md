# Contributing to wine-aa

wine-aa is an independent fork of [Wine](https://www.winehq.org). It
follows upstream Wine closely and adds its own fixes on top.

The main difference from upstream: **wine-aa accepts AI-assisted code.**
Upstream Wine does not accept code generated by AI tools, so changes made
here usually can't be sent upstream. Please don't submit wine-aa code to
Wine unless you wrote it yourself and it follows Wine's own rules.

wine-aa is not affiliated with or endorsed by the Wine project.

## Ground rules

These rules protect the project legally. A pull request that breaks them
will be closed.

### Clean room

Wine reimplements Windows, so where code comes from matters.

- **Never** use leaked, stolen or otherwise confidential Microsoft source
  code, and don't contribute if you have studied such code.
- **Never** disassemble or decompile Microsoft's DLLs or programs to write
  or check code for wine-aa.
- Black-box work is fine: public documentation, tests that call the API and
  check what it returns, and API traces of Windows programs (for example
  with `WINEDEBUG`).
- Disassembling or debugging Wine's own code, or the application you are
  trying to fix, to understand a crash is fine.

This applies to AI-generated code too: don't ask an AI tool to reproduce
Microsoft code, or to work from Microsoft binaries.

### AI-assisted code

- AI-assisted contributions are welcome.
- Say so. Add a trailer naming the tool to each commit made with AI help,
  for example `Co-Authored-By: Claude <noreply@anthropic.com>` or
  `Assisted-by: <tool name>`.
- You are responsible for the code. Read it, understand it, and test it
  before you submit it, as if you had written it yourself. "The AI wrote
  it" is not an answer in review.

### License and sign-off

wine-aa is licensed under the GNU LGPL 2.1 or later, like Wine (see
[LICENSE](LICENSE)). By contributing you agree to license your change
under the same terms.

Sign off every commit (`git commit -s`). The `Signed-off-by:` line states
that you have the right to submit the change under this license, as in the
[Developer Certificate of Origin](https://developercertificate.org).
Keep existing copyright notices intact.

## Making a change

### One fix per commit

Keep each commit to one logical change, so it can be reviewed, reverted,
or dropped on its own when upstream fixes the same bug. Use Wine's commit
message style:

```
module: Short description ending with a period.

What was wrong, why, and which application it affects.

Co-Authored-By: <tool, if any>
Signed-off-by: Your Name <you@example.com>
```

For example `msxml3/xpath: Don't parse names starting with "not" as not() in XSLPattern.`

### Add a regression test

Every fix needs a test in the module's `tests/` directory, using Wine's
test framework (`ok()`, `todo_wine`, ...). The test must fail without your
fix and pass with it.

Tests describe how Windows behaves. If you can't run the test on Windows,
explain in the commit message why you believe the expected result is
right, for example because a real application relies on it.

If your fix is in a module wine-aa hasn't changed before, add the module
to [.github/wine-aa-test-modules](.github/wine-aa-test-modules). CI always
runs the tests of the modules listed there, so later upstream merges
can't silently break your fix.

### Building and testing one module

You don't need to build all of Wine to work on one DLL. An out-of-tree
build that only compiles what you need takes seconds:

```
mkdir ../build && cd ../build
../wine/configure --enable-win64 --enable-archs=i386,x86_64
make dlls/msxml3/i386-windows/msxml3.dll dlls/msxml3/tests/i386-windows/msxml3_test.exe
wine dlls/msxml3/tests/i386-windows/msxml3_test.exe domdoc
```

Run the whole test file for the module you changed and make sure nothing
else broke. A full `make` and `make test` is still welcome before bigger
changes.

### Pull requests

- Branch from `master` and open a pull request against `master`.
- Describe the bug, how to reproduce it, and the affected application.
- Mention AI assistance in the description too.
- CI must pass before merging. It builds wine-aa and runs the tests of
  every module your pull request changes, plus the modules in
  `.github/wine-aa-test-modules`. The first build takes a while; later
  ones are faster thanks to caching.

## Following upstream

wine-aa merges new upstream Wine commits into `master` and never rewrites
`master` history, so your forks and open pull requests stay valid.

A daily job merges upstream Wine into the `upstream-sync` branch, builds
and tests it, and opens a pull request. Maintainers merge it with "Create
a merge commit". If the merge conflicts, the pull request explains how to
resolve it by hand.
If upstream fixes a bug independently, the wine-aa fix is dropped in favour
of upstream's.

## Reporting bugs

Open an issue with the Wine version (`wine --version`), the application,
steps to reproduce, and a log or `WINEDEBUG` trace if you have one.
Problems that also happen with upstream Wine can be reported to
[Wine's bug tracker](https://bugs.winehq.org) too, describing the bug
without wine-aa code.
